=== Scenario C: which runtime backends are affected (inspected, not assumed) ===
$ for b in $FM_BACKEND_KNOWN; do fm_backend_has_native_busy_state $b; fm_backend_busy_state $b some-target; done

backend  native-busy-state-capable fm_backend_busy_state('some-target')
tmux     no                     unknown
herdr    yes                    unknown
zellij   no                     unknown
orca     no                     unknown
cmux     no                     unknown

Only herdr answers busy/idle from the provider's own agent-state registry, so only herdr can
make an in-pane daemon read itself as a busy supervisor. tmux, zellij, orca and cmux report
unknown and keep the harness-native in-pane launch path (matches docs/verification/runtime-backends.md).

=== Scenario D: operator-facing contract of the in-pane entry ===
$ bin/fm-afk-start.sh --help
Enter away mode and run the sub-supervisor daemon in a harness-tracked
foreground process when one is not already alive.

Usage: fm-afk-start.sh
  Sets state/.afk unless FM_AFK_STATE_PREPARED=1, checks
  state/.supervise-daemon.lock, and:
    - prints "afk: daemon already running pid=<pid>" then exits 0 when that
      lock is held by a live daemon (a REFRESH: no stale-artifact clear);
    - otherwise clears any prior away session's stale escalation artifacts
      (fm_afk_clear_stale_artifacts) for a direct, non-prepared start, then
      execs bin/fm-supervise-daemon.sh in the foreground. A prepared start was
      already cleared transactionally by bin/fm-afk-launch.sh.
  A direct, non-prepared in-pane start on a supervisor backend that reports
  native agent state REFUSES instead: it says why, REMOVES any pre-existing
  state/.afk so away mode is never left armed with nothing supervising, and
  exits 1. Use 'bin/fm-afk-launch.sh start' there; its header owns that rule.
  The daemon lock is revalidated immediately before the "already running"
  report, so a lock holder that disappeared takes that same path.

[exit status] 0
